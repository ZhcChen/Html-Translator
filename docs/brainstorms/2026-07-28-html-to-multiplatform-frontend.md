# HTML 到多端前端代码转换

## 标题信息

- 主题：将 HTML 转换为 Vue、React 与微信小程序原生代码
- 状态：已决定
- 负责人：待定
- 日期：2026-07-28

## 背景

项目当前只有工作流骨架，尚未实现转换器。核心诉求是把 HTML 表达的界面转换成其他前端目标代码，至少覆盖 Vue、React 和微信小程序原生标签代码。

这不是简单的标签替换问题：三个目标在模板语法、属性名、事件、样式能力、组件文件组织和运行时模型上都有差异。转换器需要在可自动生成的代码、需要人工处理的逻辑和无法等价表达的能力之间给出明确边界。

## 目标

在进入执行计划前明确以下事项：

- 输入范围：HTML 片段或完整文档；是否同时接受内联样式、`<style>`、外链 CSS、脚本和静态资源。
- 输出范围：Vue、React、微信小程序分别生成哪些文件，以及默认的框架版本和编码风格。
- 语义边界：优先保持结构、样式还是交互；遇到无法安全转换的内容如何报告。
- 架构边界：避免为每个目标维护一套相互复制的字符串替换规则。
- 首个可验证版本的功能集合和验收样例。

## 约束

- 代码转换应基于 HTML/CSS 的语法树，而非正则或字符串替换。
- 输入中的任意 JavaScript 不能直接执行，也不能声称可以无损转换为各平台运行时代码。
- 微信小程序不是浏览器环境，DOM、CSS、事件和组件模型都存在能力差异。
- 目标代码应保持可读、可格式化，并输出结构化诊断，而不是静默丢弃内容。
- 每个目标的生成结果应能独立验证，使用固定 fixture 做快照或语法检查。
- 映射规则必须集中定义、可按目标版本测试；生成器只消费规则和中间表示，不能内嵌零散的标签或样式特例。
- 对微信小程序的 CSS 兼容性应以目标基础库版本为准，保留可兼容样式并报告风险，不能以不透明的自动删改代替诊断。

## 备选方案

### 方案 1：为每个目标直接编写 HTML 到目标代码的转换器

- 概述：分别实现 HTML -> Vue、HTML -> React、HTML -> WXML 的转换规则。
- 优点：首个目标上线快，概念直接。
- 缺点：标签、属性、样式和诊断规则会在多个转换器中重复；新增目标或修正规则时容易不一致。
- 风险：复杂 HTML、CSS 和交互逐步加入后，维护成本会快速上升。

### 方案 2：HTML/CSS AST -> 跨端 UI 中间表示 -> 各目标生成器

- 概述：先解析 HTML 和 CSS，归一化为包含节点、属性、样式、资源引用、绑定和源码位置的中间表示，再由各目标生成器渲染代码。
- 优点：公共语义、能力检查和诊断只实现一次；新增目标只需实现映射与生成器；适合 fixture 驱动测试。
- 缺点：首期需要设计中间表示和能力注册表，初始投入较高。
- 风险：中间表示设计过宽会拖慢 MVP；需从静态界面能力开始，按用例扩展。

### 方案 3：以大模型为主要转换引擎

- 概述：将源代码和目标要求直接交给模型生成目标代码。
- 优点：能覆盖非结构化说明和部分复杂迁移建议。
- 缺点：输出不稳定、难以做可重复测试，也无法可靠保证语义、样式与安全边界。
- 风险：成本、隐私和可复现性均不适合作为核心编译链路。

### 方案 4：以跨端框架作为统一开发入口

- 概述：新增业务页面直接使用 `uni-app` 的 Vue 组件或 Taro 的 React/Vue 组件开发，由框架编译为微信小程序与其他端代码；仅把转换器用于导入历史 HTML 或静态原型。
- 优点：框架已处理数据绑定、事件代理、页面配置和多端运行时，能显著减少手写原生 WXML/WXSS/JS 的工作量。
- 缺点：不能将任意浏览器 HTML、CSS、JavaScript 无损转换为可维护的跨端工程；团队必须遵守框架组件与 API 边界。
- 风险：依赖 DOM、浏览器专属 API 或 Web 组件的现有页面仍需人工改造。

## 映射规则模型

映射规则应是编译器的独立模块，每个目标各自声明标签、属性、事件、样式和诊断规则。建议规则接口至少表达：

- 输入匹配条件：源标签、属性、属性值、子节点类型和上下文。
- 输出定义：目标标签、目标属性、属性值转换和是否需要生成附属代码。
- 前置条件：例如链接是否为小程序内部路由、事件值是否只是函数标识符。
- 兼容级别：无损、近似转换、需要人工处理、不支持。
- 诊断信息：源码位置、原因、建议处理方式和适用目标版本。

Vue 与 React 的规则主要处理模板语法差异，样式默认原样保留：

| 源 HTML | Vue 3 | React TSX |
| --- | --- | --- |
| `class` | `class` | `className` |
| `for` | `for` | `htmlFor` |
| `onclick="handleClick"` | `@click="handleClick"` | `onClick={handleClick}` |
| CSS 类选择器 | 原样保留 | 原样保留 |

只有当事件值是可识别的函数标识符时才允许自动生成事件绑定。`onclick="doSomething(a + 1)"`、`<script>` 和 DOM 操作应保留为诊断，不生成看似可运行但实际错误的代码。

微信小程序需要单独的 `wxml` 与 `wxss` 规则集。初始标签映射建议如下：

| 源 HTML | WXML 默认输出 | 规则说明 |
| --- | --- | --- |
| `div`、`section`、`main`、`article`、`header`、`footer`、`nav`、`aside` | `view` | 小程序没有对应语义容器；保留 `class`、`id`、`data-*`，并记录语义降级。 |
| `span`、`strong`、`em` 等仅含文本的行内节点 | `text` | 仅在子树可以作为文本内容表达时使用；含图片、布局容器等子节点时降级为 `view`。 |
| `p`、`h1` 至 `h6` | `view` | 默认保留块级布局语义；纯文本可直接作为内容，后续可按样式规则增加 `text` 包装。 |
| `img` | `image` | 转换 `src`、`alt`；根据 `object-fit` 推导 `mode`，无法等价时给出警告。 |
| `button` | `button` | 保留可兼容属性；点击事件使用 `bindtap`。 |
| `input`、`textarea` | `input`、`textarea` | 转换常用表单属性和受限事件。 |
| 小程序内部 `a[href]` | `navigator` | 仅当 `href` 可识别为应用内页面路径；外部链接需诊断。 |
| `select` / `option`、`table`、`iframe` | 无直接映射 | 标记为需要人工改为 `picker`、嵌套 `view` 或目标组件。 |

WXSS 应先尽可能保留原有 CSS，而不是默认把 `px` 转为 `rpx`。小程序的 WXSS 具备大部分 CSS 特性，并额外提供 `rpx`；单位策略应作为配置项，例如 `preserve`、`px-to-rpx` 或自定义转换。转换器需要解析 CSS，并对目标基础库版本不支持或语义变化明显的选择器、属性和值生成诊断。完整文档中的 `html`、`body` 样式可尝试映射到小程序页面根样式，但必须标记为近似转换。

## 当前倾向

采用方案 2，并将首个版本限制为“静态 HTML + 可解析 CSS”的确定性转换器。转换核心使用 Rust 实现，协议适配层通过 MCP stdio 供本地 AI agent 调用。

若项目的首要目标是减少今后业务页面的原生小程序开发，而不是迁移存量 HTML，则应优先采用方案 4：Vue 团队选择 `uni-app`，React 团队选择 Taro；本项目则收缩为历史 HTML/原型导入工具和映射诊断器。两条路径可以共存，但不能把跨端框架误认为任意 HTML 的无损代码生成器。

建议的编译链路如下：

1. 用 HTML 解析器生成 `SourceDocument`，保留元素、文本、常用属性、类名、内联样式和源码位置。
2. 用 CSS 解析器生成样式规则，并归入跨端 UI 中间表示。
3. 使用目标能力注册表处理标签、属性、事件和 CSS 的映射，同时生成诊断。规则需要按目标平台与版本声明，而不是写死在代码生成分支中。
4. 输出目标文件包，而不是单段文本：Vue 生成 `.vue`，React 生成 `.tsx` 与样式文件，微信小程序生成 `.wxml`、`.wxss`、`.js`、`.json`。
5. 将每一项转换标记为“原样保留”“已改写”“需要人工处理”或“不支持”，方便调用方展示报告。

建议 MVP 支持：

- 常见静态结构：`div`、`span`、`p`、标题、列表、图片、链接、表单基础控件。
- 常用属性：`id`、`class`、`data-*`、`src`、`alt`、`href`、`title`、`aria-*`。
- 内联样式和 `<style>` 中的基础选择器、布局及文字样式。
- Vue 3 模板、React TSX 和微信小程序 WXML 的基础标签/属性映射。
- Vue、React 和小程序的初始映射规则表已在本文件的“映射规则模型”中定义，后续以真实 fixture 校准。
- 微信小程序保留兼容的 CSS；`px` 到 `rpx` 的换算仅作为可选策略，不作为默认行为。
- 对 `onclick`、`<script>`、DOM 查询、外链样式、复杂选择器和目标平台不支持的 CSS 输出明确警告。

MVP 不承诺自动迁移任意 JavaScript、第三方组件、复杂动画、浏览器专属 API 或完整响应式状态管理。

## 待确认问题

- 输入是纯 HTML 字符串，还是包含 HTML、CSS、JS、图片等资源的项目目录？
- 首期是否只要求静态页面转换，还是必须把事件和数据绑定一并生成？
- 项目的首要目标是迁移已有 HTML，还是让后续业务不再手写原生小程序？前者应建设转换器，后者应优先选择 Taro 或 `uni-app`。
- Vue 的目标版本是否固定为 Vue 3；React 是否使用 TypeScript/TSX；小程序是否固定为原生微信小程序而非 `uni-app`、Taro？
- 输出形态需要命令行工具、HTTP API、网页编辑器，还是先提供可调用的库？
- 样式的验收优先级是什么：结构正确、视觉接近、还是交互可运行？
- 是否有必须优先支持的真实 HTML 样例，可作为第一批 fixture 和验收基准？
